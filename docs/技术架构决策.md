### D1 · Express

**方案**：后端使用 Express。

**理由**：够用、资料最多、学习成本最低。MVP 的核心链路是纯文本生成，没有复杂后端需求。

**约束**：后端只需承载 3 个业务端点与 1 个健康检查端点。

### D2 · `@anthropic-ai/sdk`

**方案**：使用官方 SDK 调用模型，不用原生 `fetch` 手写请求。

**理由**：官方维护、错误处理与重试语义清晰、参数类型明确。

**约束**：API Key 只存在于后端，**绝不下发到浏览器**。因此本作品不能是纯静态页面，必须有可运行的服务端进程。

### D3 · 确定性输入检查 + 一次正式生成

**方案**：程序先做确定性输入检查（必填、枚举、范围）；检查通过后，正式生成**一次** AI 调用。**不设单独的"AI 预检查"接口。**

**关键澄清**：「一次 AI 调用」指的是**一次具体操作对应一次正式 AI 调用**，不是整个产品生命周期只能调用一次。

| 操作 | AI 调用 |
|---|---|
| 批量生成 | 一次，返回 5–10 篇 |
| 单篇换风格重写 | 一次，只生成这一篇 |
| 重新评分 | 一次，只返回 score |

**理由**：多一次预检查调用＝多一倍成本与延迟，而确定性检查（必填、枚举、范围）本来就该由程序完成，不需要 AI。

**约束**：质量兜底不能靠"先探一次路"，只能靠生成之后的校验与重试机制（见 D8）。

### D4 · MVP 不做流式输出

**方案**：一次性完整返回，不做流式。

**理由**：流式是横跨全栈的改造（模型调用、Express、前端三处），而 MVP 的核心是跑通链路。流式作为「后续升级台阶」保留。

**约束**：用户是"等待 → 一次性拿到结果"，**如果拿到的是坏数据，没有任何渐进补救余地**。因此后端必须在返回前拦住坏数据——这是 D8 存在的直接原因。

### D5 · React 内置 `useReducer` + Context

**方案**：不引入 Zustand / Redux，使用 React 内置的 `useReducer` + Context。

**理由**：状态结构单一（一个页面、一棵状态树），内置能力足够；不增加依赖与学习成本。

**约束**：状态设计与 action 语义必须事先定义清楚（见第 11 节）。

### D6 · 单一工程双入口

**方案**：一个工程、一份依赖、一次安装；前端与后端各有启动入口。

```
app/src/       前端
app/server/    后端
app/shared/    前后端共享类型与规则
app/prompts/   提示词
```

**理由**：无需拆成两个仓库；`app/shared/` 可以承载**前后端共享的枚举与校验规则**，避免规则抄成两份。

### D7 · 作品使用独立仓库

**方案**：本仓库（`E:\AI-Projects\xiaohongshu-copy-studio`）为独立产品仓库，与学习仓库 `ClaudeCode-Learning` 并列，**不嵌套**。

**理由**：清晰的产品工程边界；便于 GitHub 展示、部署与持续迭代；学习仓库保留为纯学习仓库。

**约束**：本仓库有自己的 `CLAUDE.md`、`.gitignore`、依赖与提交历史。

**PRD 的处理**：Day 1 PRD 复制一份到本仓库，**本仓库中的版本为后续持续维护的权威版本**；学习仓库中的版本保留为 Day 1 快照、不再修改。

### D8 · 严格 JSON 校验 + 最多重试一次

**方案**：

1. **严格校验**：先 JSON 解析，再做 Schema / 数据结构校验。**解析失败与结构校验失败分别处理**（两者性质不同：前者连对象都拿不到，后者对象拿到了但内容不合格）。
2. **失败最多自动重试一次**。
3. **重试时把第一次失败的具体原因反馈给模型**，不是简单原样重发。
4. **第二次仍失败**：不再重试；后端返回结构化错误；前端保留用户输入；**绝不把半成品数据交给前端**。

**理由（与 D3、D4 配套）**：

- D3 决定了质量兜底只能靠"校验 + 重试"，不能靠预检查
- D4 决定了坏数据必须在后端被拦下，否则前端只能整体失败
- 上限定为 1：偶发失败重试一次大概率成功；系统性失败重试五次只是多烧钱。**最坏成本 2 倍，有限且可预估。**

**暂不纳入 D8 的部分**：API Key、网络、超时、余额等**调用层错误**，留到后续错误处理阶段（类型先占位，见第 5 节）。

**暂不包含**：「对模型输出的清理」细则，作为实现阶段需进一步定义的问题，不在 D8 范围内扩大。

### 2.1 语言与共享形式

**前后端统一使用 TypeScript。**

`app/shared/` **直接共享 TypeScript 源码**：**不创建额外的 npm package，不使用 monorepo / workspace**。

| 项 | 决定 |

## 3. 统一处理管线

三个业务端点共用**同一条内部管线**，只有两处不同：**用什么提示词**、**返回什么形状**。

```
请求
 → 确定性输入检查
 → 计算 style allocation（仅 generate）
 → Prompt 组装
 → AI 调用
 → JSON 解析
 → Schema 校验
 → 校验实际 style 分布是否符合 allocation（仅 generate）
 → 失败最多重试一次
 → 返回成功结果或结构化错误
```

**原则：端点划分 ≠ 逻辑重复。** 三个端点只是三道门，门后是同一条管线；校验函数复用同一套，不存在第二套实现。

## 4. API 契约

### 4.1 `GET /api/health`

仅用于本地确认后端在运行、演示前快速排障。**不承载业务逻辑。**

### 4.2 `POST /api/generate`

**请求**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `product` | string | 是 | 产品或主题 |
| `selling_points` | string[] | 是 | 卖点，**前端已拆分为独立条目** |
| `styles` | string[] | 是 | 用户选中的风格，至少 1 个，值域＝4 个基础风格 |
| `count` | integer | 否 | 5～10，不传则默认 6 |

**成功响应（HTTP 200）**

```
{
  "information": {
    "status": "sufficient" | "limited",
    "message": "一句中文提醒（status 为 sufficient 时为空字符串）"
  },
  "notes": [note, ...]       // 长度必须等于 count
}
```

**`information` 是辅助字段**（2026-09-26 确认，方案 A2）：由 AI 原始输出的 `information_status` / `information_message` **映射**而来，使对外契约与 Prompt 内部字段名解耦。

**它不参与严格 Schema 校验**：

| 情况 | 处理 |
|---|---|
| `notes` 缺失或非法 | `SCHEMA_FAILED` → 最多重试一次 |
| `information` 缺失或非法 | **不触发重试**，降级为 `{ "status": "sufficient", "message": "" }` |

`notes` 仍必须严格校验。（前端展示位置：结果区信息条；本阶段只定契约，UI 后置。）

### 4.3 `POST /api/rewrite`

**请求**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `product` | string | 是 | 原始产品/主题 |
| `selling_points` | string[] | 是 | 原始卖点 |
| `target_style` | string | 是 | **目标新风格**，值域＝4 个基础风格 |
| `current_note` | object | 是 | 含 `title`、`body`、`hashtags`、`content_directions`、`style` |

> **命名说明**：顶层用 `target_style`（目标风格），与 `current_note.style`（当前风格）区分，避免同一请求里出现两个 `style` 造成误用。

**成功响应（HTTP 200）**

```
{ "notes": [note] }          // 长度固定为 1
```

**重写要求**：尽可能保持当前文案的信息资产——原始产品、原始卖点、title/body 中的事实信息、hashtags、content_directions。**目标是改变表达风格，不是改变内容事实或内容方向**；允许按目标风格调整表达，**不得编造信息**。

### 4.4 `POST /api/score`

**请求**（全部必填）

| 字段 | 类型 | 说明 |
|---|---|---|
| `title` | string | 待评分标题 |
| `body` | string | 待评分正文 |
| `style` | string | 当前风格（`style_match` 的依据） |
| `content_directions` | string[] | 内容方向 |
| `product` | string | 原始产品 |
| `selling_points` | string[] | 原始卖点 |

> `product` 与 `selling_points` 必带：`information_completeness`（信息完整度）**必须以用户原始输入作为对照基准**，否则该维度会空泛。

**成功响应（HTTP 200）**

```
{ "score": { total, title_attractiveness, readability, identification,
             style_match, information_completeness, strength, improvement } }
```

**只返回 `score`，不返回 `notes`。**

**语义**：一次独立 AI 调用，只评价当前文案，**不重写、不改变任何文案字段**。

### 4.5 派生数据

`generated_count` 与 `average_score` **由前端从 `notes` 派生计算**，后端不重复返回：

- `generated_count` = `notes.length`
- `average_score` = `notes` 中 `score.total` 的算术平均值

**`average_score` MVP 阶段计算并保留，但不在信息条展示**（作为结果数据的确定性派生值，供未来统计/排序等扩展使用）。

### 4.6 端点划分的依据

采用**三个独立业务端点**，而非单端点 + `action` 参数：

- 三个操作的**输出形状本就不同**（`notes[]` 长度 N / 长度 1 / 仅 `score`），单端点会让契约变成"看 action 才知道是什么"的联合体
- **错误归属天然清晰**：端点与状态粒度一一对应（generate→区域级，rewrite/score→卡片级）
- **加操作时不动已有契约**

## 5. 统一错误契约

**形状**

```
{
  "error": {
    "type": "INVALID_INPUT",
    "field": "product",
    "message": "请填写产品名称",
    "detail": "..."
  }
}
```

**类型枚举**

| `type` | 含义 | HTTP |
|---|---|---|
| `INVALID_INPUT` | 确定性输入检查未通过 | 400 |
| `PARSE_FAILED` | 重试后仍解析失败 | 502 |
| `SCHEMA_FAILED` | 重试后仍结构校验失败 | 502 |
| `AI_CALL_FAILED` | 调用层错误（Key / 网络 / 超时 / 余额）—— **判定规则推迟** | 502 / 503 |
| `INTERNAL` | 兜底 | 500 |

**字段说明**

- `type`：给程序使用
- `field`：**可选**，仅 `INVALID_INPUT` 提供；使后端错误能落到对应字段的行内位置，与前端本地校验共用同一条渲染路径
- `message`：给用户使用，**中文**，说清"应该怎么改"
- `detail`：仅给开发/排障使用，**界面永不渲染**

**三条原则**

1. 界面只展示 `message`，永不展示 `detail`
2. `type` 给程序，`message` 给人，两者不可混用
3. 不暴露技术实现细节（不出现 JSON、Schema、token 等词汇）

**前端不做自动重试**；重试次数由后端 D8 规则控制。

## 6. AI 输出契约

**顶层信封（三条路径各不相同）**

| 路径 | AI 原始输出的顶层结构 |
|---|---|
| generate | `{ information_status, information_message, notes[] }` |
| rewrite | `{ notes[] }`（长度固定 1） |
| score | `{ score }` |

其中 generate 的 `information_status` / `information_message` 是**辅助字段**，会被 API 层映射为响应的 `information.{status,message}`（见 4.2 节）。

**单篇 note 结构（三条路径共用）**

```json
{
  "title": "...",
  "body": "...",
  "hashtags": ["...", "..."],
  "content_directions": ["...", "..."],
  "style": "...",
  "score": {
    "total": 86,
    "title_attractiveness": 22,
    "readability": 23,
    "identification": 17,
    "style_match": 13,
    "information_completeness": 11,
    "strength": "...",
    "improvement": "..."
  }
}
```

**`hashtags` 的值不带 `#`**（如 `["护手霜", "秋冬护肤"]`），由**程序**在页面展示与最终复制文本时统一添加 `#`。Schema 校验要求 `hashtags` 每一项为纯标签文本、**不含前导 `#`**。

**AI 不返回**：`generated_count`、`average_score`（程序计算）。

**`persona` 字段不存在**：本系统**不设**「人设」概念，不新增 `persona` 字段或 UI。有效概念只有 `style`（风格）与 `content_directions`（内容方向）。

## 7. 评分规则

**由 AI 在同一次正式调用中完成文案生成与辅助评分**，不增加额外的评分 AI 调用。

| 维度 | 字段名 | 上限 |
|---|---|---|
| 标题吸引力 | `title_attractiveness` | 25 |
| 可读性 | `readability` | 25 |
| 用户认同感 | `identification` | 20 |
| 风格匹配度 | `style_match` | 15 |
| 信息完整度 | `information_completeness` | 15 |
| **总分** | `total` | **100** |

另含：`strength`（一句具体优势）、`improvement`（一句具体改进建议）。

**定位声明**：评分只是「爆款潜力自评」的**辅助参考**，**不是对真实流量、点赞、转化或爆款概率的预测**。不得把评分重新定义为流量预测，不设计「爆款概率」。

## 9. 风格分配规则（程序预分配）

**由后端程序确定性分配，AI 不决定各风格生成几篇。**

**规则**：先每个选中风格各 1 篇，剩余篇数按**固定枚举顺序轮转**分配。

**轮转顺序 = 风格枚举顺序**：亲切分享 → 专业测评 → 搞笑段子 → 干货攻略

**不使用用户勾选顺序**（勾选顺序对用户不可见、不可预期，会破坏确定性）。

**示例 1**：选中〔亲切分享、搞笑段子、干货攻略〕，`count = 7`

```
先各 1 篇（用掉 3，剩 4）
轮转 3 篇：亲切 +1、搞笑 +1、干货 +1（剩 1）
剩 1 篇给顺序最前者：亲切 +1
结果：亲切分享 3 · 搞笑段子 2 · 干货攻略 2 = 7
```

**示例 2**：4 个风格全选，`count = 6`

```
先各 1 篇（用掉 4，剩 2）
轮转 2 篇：亲切 +1、专业 +1
结果：亲切分享 2 · 专业测评 2 · 搞笑段子 1 · 干货攻略 1 = 6
```

**前提**：`count`（5～10）永远 ≥ 风格数量（1～4），因此"每个选中风格至少 1 篇"**永远可满足**。

**位置**：分配在后端计算（要写进 Prompt，也要用于校验）。**前端不参与分配**，只从最终 `notes` 做展示层统计。

## 10. 校验规则

### 10.1 确定性输入检查（前后端共享同一份规则）

| 检查项 | 规则 | `field` |
|---|---|---|
| 产品 | 非空、长度上限 | `product` |
| 卖点 | 非空（至少 1 个非空卖点） | `selling_points` |
| 风格 | 至少 1 个 | `styles` |
| 风格 | 必须属于允许的 4 个基础风格 | `styles` |
| 篇数 | 必须为整数 | `count` |
| 篇数 | 范围 5～10 | `count` |
| 篇数 | 未填写时使用默认值 6 | —— |
| 篇数 | `count >= styles.length`（防御性；MVP 值域下恒成立，保留检查） | `count` |

**规则只维护一份**，放在 `app/shared/`：枚举、范围、默认值、必填规则、字段格式/长度规则。**前端负责体验层面的提前拦截，后端负责最终权威校验。**

### 10.2 结果结构校验（D8）

**先解析，再校验。两类失败分别处理：**

| 类别 | 含义 |
|---|---|
| **解析失败**（`PARSE_FAILED`） | 文本不是合法 JSON，连对象都拿不到 |
| **结构校验失败**（`SCHEMA_FAILED`） | 是合法 JSON，但内容不符合要求 |

**解析前的最小预处理（结构化解析层，2026-09-26 确定并实现）**

在 `JSON.parse` 之前，**只允许做一件事：剥离最外层的 code fence**。

| 情况 | 行为 |
|---|---|
| ` ```json … ``` ` | ✅ 剥离外层围栏后解析 |
| ` ``` … ``` `（无语言标记） | ✅ 剥离外层围栏后解析 |
| 围栏之外还存在其他文字（如前后说明语） | ❌ **不剥离**，直接进入 `JSON.parse` 失败流程 |
| 非 `json` 的语言标记（如 ` ```javascript `） | ❌ 不剥离 |
| 缺少收尾围栏 | ❌ 不剥离 |

**只剥离外层围栏**：不做 JSON 自动修复、不补括号、不补引号、不猜测字段、不做任何语义修改。

**剥离后仍必须经过完整的 `JSON.parse` + Schema 校验**——预处理只改变解析输入，**不绕过任何校验**。

未剥离或剥离后仍非法时，按 D8 走「解析失败 → 最多重试一次」。

**`notes` 结构校验**：`notes` 存在且为数组；每项 `title` / `body` 非空字符串；`hashtags` 为字符串数组且每项不含前导 `#`；`content_directions` 为字符串数组且值域＝8 个内容方向；`style` 在 4 个基础风格内；`score` 结构完整。

**`score` 校验**：

- `title_attractiveness`：0～25
- `readability`：0～25
- `identification`：0～20
- `style_match`：0～15
- `information_completeness`：0～15
- `total` 必须**等于**五个维度之和
- `total` 范围 0～100
- `strength`、`improvement` 必须为字符串

### 10.3 分配校验（仅 generate）

1. 每篇 `note` 的 `style` 必须**属于用户选中的 styles**
2. 按 `style` 分组后的实际篇数必须**严格等于后端预分配表**
3. `notes.length` 必须等于 `count`

## 11. 前端状态设计（`useReducer` + Context）

### 11.1 四个设计前提

| # | 前提 | 原因 |
|---|---|---|
| 1 | **每篇笔记由前端分配 `localId`**，`localId` **绝不进入 AI 契约** | 卡片级状态需要稳定身份；AI 不返回 id，也不该返回 |
| 2 | **编辑草稿与正式 note 分离** | 「取消」要能还原；直接改 note 则无法恢复 |
| 3 | **重写成功 = 替换内容，但保留 `localId`** | 若换新 id，该卡的编辑/评分状态会错位 |
| 4 | **新一轮生成成功 = 整体替换 notes 并重置所有卡片状态** | 新一轮结果是全新集合 |

### 11.2 State 结构

**顶层分组**：`form` · `errors` · `batch` · `notes` · `cards`

**`form`**

| 字段 | 类型 | 说明 |
|---|---|---|
| `product` | string | 产品/主题 |
| `sellingPoints` | string[] | 已拆分好的卖点 |
| `sellingPointDraft` | string | 卖点输入框当前内容（尚未成为标签） |
| `styles` | string[] | 选中风格，**按固定枚举顺序存放** |
| `count` | number | 篇数，默认 6 |

**`errors`**：`{ product?, sellingPoints?, styles?, count? }`，每个值是一条中文提示

**`batch`**：`{ status: 'idle' | 'loading' | 'error', error: {type, message} | null }`

**`notes`**：数组，每项 = 契约 note 字段 + `localId`

**`cards`**：`{ [localId]: CardState }`

| CardState 字段 | 类型 | 说明 |
|---|---|---|
| `view` | `'display' \| 'edit' \| 'rewrite'` | 卡片当前形态 |
| `draft` | `{ title, body } \| null` | 编辑草稿，仅 `edit` 态存在 |
| `targetStyle` | `string \| null` | 重写态选中的目标风格（**失败后保留**，见 12.2） |
| `status` | `'idle' \| 'rewriting' \| 'scoring'` | 卡片级操作状态 |
| `scoreStale` | boolean | 编辑保存后置 `true`；重写成功 / 重新评分成功后置 `false` |
| `error` | `{ type, message } \| null` | 卡片级错误（重写失败 / 评分失败） |
| `copyFeedback` | `'idle' \| 'copied' \| 'failed'` | 复制按钮临时反馈 |

**不放进 state 的派生数据**：`generated_count`、`average_score`、信息条中的风格分布。

### 11.3 Action 语义

**表单与校验**

| Action | 作用 |
|---|---|
| `SET_PRODUCT` | 改产品名 |
| `SET_SELLING_POINT_DRAFT` | 改卖点输入框 |
| `ADD_SELLING_POINT` | 把输入框内容添加为标签（程序负责拆分整理） |
| `REMOVE_SELLING_POINT` | 删除一个卖点标签 |
| `TOGGLE_STYLE` | 选中/取消一个风格 |
| `SET_COUNT` | 改篇数 |
| `VALIDATION_FAILED(errors)` | 提交时校验失败，写入全部字段错误 |
| `CLEAR_FIELD_ERROR(field)` | 用户开始修改某字段时，清除该字段错误 |

**批量生成（区域级）**

| Action | 作用 |
|---|---|
| `GENERATE_START` | `batch.status = 'loading'`；**不清空 notes** |
| `GENERATE_SUCCESS(notes)` | 整体替换 notes、分配 `localId`、重建 cards、清空区域错误 |
| `GENERATE_FAILURE(error)` | 区域级错误；**保留旧 notes**（失败后旧结果可恢复显示） |

**本地编辑（卡片级，不调 AI）**

| Action | 作用 |
|---|---|
| `BEGIN_EDIT(localId)` | `view='edit'`，`draft` 初始化为当前内容 |
| `UPDATE_DRAFT(localId, patch)` | 改草稿 |
| `COMMIT_EDIT(localId)` | 写回 note，`scoreStale = true`，回 `display` |
| `CANCEL_EDIT(localId)` | 丢弃草稿，回 `display` |

**换风格重写（卡片级，调 AI）**

| Action | 作用 |
|---|---|
| `BEGIN_REWRITE(localId)` | `view='rewrite'`，`targetStyle=null` |
| `SET_TARGET_STYLE(localId, style)` | 选目标风格（**不触发调用**） |
| `CONFIRM_REWRITE(localId)` | `status='rewriting'`，发请求 |
| `REWRITE_SUCCESS(localId, note)` | 替换该卡内容，**保留 localId**，`scoreStale=false`，清除 `targetStyle` 与 `error`，回 `display` |
| `REWRITE_FAILURE(localId, error)` | 回 `display`，原文案不变，**保留 `targetStyle`**，写入 `error` |
| `CANCEL_REWRITE(localId)` | 回 `display`，原文案不变，清除 `targetStyle` 与 `error` |

**重新评分（卡片级，调 AI）**

| Action | 作用 |
|---|---|
| `REQUEST_SCORE(localId)` | `status='scoring'` |
| `SCORE_SUCCESS(localId, score)` | 更新该卡 `score`，`scoreStale=false` |
| `SCORE_FAILURE(localId, error)` | 卡片级错误；**原有评分不清空** |

**复制反馈**

| Action | 作用 |
|---|---|
| `SET_COPY_FEEDBACK(localId, 'copied' \| 'failed')` | 按钮短暂反馈 |
| `RESET_COPY_FEEDBACK(localId)` | 约 2 秒后复位 |

> Action 命名在实现时可微调，但**必须保持上述语义与职责边界**。

## 12. 卡片级交互

### 12.1 就地编辑

**就地展开编辑，不使用浮层 / 模态框 / 侧边抽屉。**

| 规则 | 内容 |
|---|---|
| 进出 | 「完成 / 取消」明确结束；**不做自动保存** |
| 高度 | 编辑态保持合理的最小高度，减少页面跳动 |
| 调用 | **普通编辑只修改前端本地状态，不调用 AI** |
| 操作区 | 编辑态下**隐藏「复制」与「换风格重写」**，避免操作对象处于未确认状态产生歧义 |

### 12.2 换风格重写

**交互**：点「换风格重写」→ 卡片进入重写态 → 展示可选目标风格 → 用户选目标风格 → 点「确认重写」→ **才正式调用 AI**；同时提供「取消」。

**选择风格后不得立即调用**，必须经过确认——该操作有真实成本（AI 调用 + 等待），不应一步触发。

**语义**：一次独立 AI 调用，只生成这一篇；返回统一契约中的 `notes` 数组，长度固定为 1；复用确定性输入检查、JSON 解析、Schema 校验、最多重试一次、结构化错误——**不为重写单独实现另一套校验体系**。

**重写输入**：`product`、`selling_points`、`target_style`、`current_note`（含 title / body / hashtags / content_directions / style）。

**约束**：保留核心事实、核心卖点、当前内容方向；不改变产品事实；只改变表达方式、语言风格与呈现方式；不因换风格而强行更换内容角度；不为符合新风格而编造信息。**它是「同一篇文案的另一种风格版本」，不是重新生成一篇无关文案。**

**状态粒度**：卡片级。只有当前卡片进入 `rewriting`，其他卡片继续正常显示和操作。

**失败处理**：只在当前卡片显示错误并提供重试；不影响其他卡片；不清空用户当前输入；不清空其他已生成结果。**失败后保留 `targetStyle`**，使「重试」可直接复用原目标风格（无需用户重新选择）。用户主动取消该失败状态时，才清除 `targetStyle` 与 `error`。

**次数**：**不限制**，用户可对同一篇反复重写。

**版本**：重写成功后**新文案直接替换当前卡片**。**MVP 不做版本历史、版本对比、撤销历史**。用户点「取消」则本次重写操作取消，保留原文案。

### 12.3 重新评分

**属于 MVP 功能。**

**触发**：用户手动编辑当前文案后，原评分标记为可能过时（`scoreStale = true`），用户点击「重新评分」。**未修改文案时也允许主动点击。**

**语义**：一次独立 AI 调用；只评价当前文案；**不进行重写**；**不改变** `title` / `body` / `hashtags` / `content_directions` / `style`；只返回新的 `score`；复用 JSON 解析、Schema 校验、最多重试一次、结构化错误。

**状态粒度**：卡片级。

### 12.4 `localId` 规则

- 由**前端**在收到结果时分配，**绝不进入 AI 契约**
- 重写成功替换内容时**保留原 `localId`**
- 新一轮生成成功时**全部重新分配**，并重建 cards 映射

## 13. 错误 UI 落点

### 总原则：落点 = 出错操作的影响范围

| | 区域级错误 | 卡片级错误 |
|---|---|---|
| 触发 | 批量生成失败 | 换风格重写失败、重新评分失败 |
| 影响范围 | 整个结果区 | 单张卡片 |
| **落点** | **结果区顶部——信息条的位置** | **卡片内部——紧贴出错的操作处** |
| 视觉权重 | 较高（配重试按钮） | 低调 |
| 其他区域 | 左栏输入区完全不变 | 其他卡片完全不受影响 |

**两处复用同一种错误组件语义**（「错误文案 + 重试按钮」），仅按影响范围调整位置与视觉权重——**不写两套错误 UI**。

### 13.1 区域级错误

位置：占据信息条位置。包含三个要素：

1. 一行错误文案
2. 一句状态说明「**以下是上一次的结果**」——必需，否则用户不知道屏幕上的内容从哪来
3. 「重试」按钮

| 错误类型 | 文案 |
|---|---|
| `PARSE_FAILED` / `SCHEMA_FAILED` | 生成结果格式异常，请重试或调整输入后重试 |
| `AI_CALL_FAILED` | AI 服务暂时不可用，请稍后重试 |
| `INTERNAL` | 生成失败，请重试 |

**旧结果完全保留**，仍可编辑、复制、换风格重写、重新评分。错误态下**信息条（统计）隐藏**，由错误条占据该位置。

**空态下失败**：错误条显示在上方，下方继续显示空态引导。

**重试语义**：使用**当前表单内容**重新发起一次生成；**先重新执行前端校验**，通过后才发请求。若表单已不合法，触发与本地校验相同的行内字段提示。

### 13.2 卡片级错误

**重写失败**：卡片回浏览态，原文案完整保留，在操作区附近显示「换风格重写失败，请重试」+ 重试按钮。

**评分失败**：在评分区域显示「评分失败，请重试」+ 重试按钮；**原有评分保留、不清空**。

**重试语义**：重写重试 = 用保存的 `targetStyle` 再试一次；评分重试 = 用当前卡片内容再试一次。

### 13.3 明确不做

全局 Toast · 页面顶部错误横幅 · Modal · 前端自动重试 · 任何位置展示 `detail`。

## 14. 复制规则

**复制「当前卡片的可发布内容」**：

```
标题
（空行）
正文
（空行）
#标签1 #标签2 #标签3
```

**不复制**：风格标签、内容方向标签、`score`（含 `strength` / `improvement`）、任何界面装饰文字。

**对象是卡片最终状态**：包含用户的就地编辑结果、包含换风格重写后的新版本；**不恢复成原始生成版本**。

**反馈**：点击后按钮变为「已复制 ✓」，约 2 秒后恢复「复制」。**不使用全局 Toast、不使用弹窗。**

**失败**：按钮显示「复制失败」，约 2 秒后恢复，可再次尝试；不弹窗、不展示技术错误。

**`#` 的渲染**：数据层 `hashtags` 不带 `#`，由**程序**在页面展示与复制文本时统一添加。
